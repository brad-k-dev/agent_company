# AI Agent Company — 기획 · 설계

## 1. 무엇을 만드는가

CEO(사용자)가 한 줄로 지시하면("메모 iOS앱을 만들어") 6개 팀이 차례로 일하고
결과물을 다음 팀에 넘겨, **리서치 → 기획 → 디자인 → 개발 → QA → 배포 준비**까지
끝내는 Claude Code 스킬 묶음.
자동 흐름은 QA까지다. 배포 준비는 사용자가 결과를 보고 직접 시작한다.

| 진입점 | 누가 지시를 받나 | 하는 일 |
|--------|----------------|--------|
| `/agent-company:company <지시>` | 리서치~QA 5개 팀 | 순서대로 자동 진행 |
| `/agent-company:team-<팀> <지시>` | 그 팀 리더 | 한 팀만 일 시킴 (research·planning·design·dev·qa) |
| `/agent-company:release [지시]` | 배포준비팀 리더 | 배포 준비 + 사용자가 할 일 목록. 실제 업로드·심사 제출은 하지 않는다 |

`agent-company` 플러그인으로 배포한다. 결과물은 앱을 만들 폴더에 생겨야 하므로
스킬 저장소에 묶인 프로젝트 스킬이 아니라 어디서나 설치해 쓰는 플러그인이어야 한다.

## 2. 조직

팀마다 리더 1명 + 팀원 2명. 총 18명. 모두 **별도 서브에이전트**이고
각자 이름·성격·전문 관점·도구 권한·모델이 다르다. 명단과 페르소나는 `agents/*.md`가 정본이다.

| 팀 | 최종 산출물 |
|----|-----------|
| research | `01-research.md` |
| planning | `02-planning.md` |
| design | `03-design.md` |
| dev | `app/`, `04-dev.md` |
| qa | `05-qa.md` (마지막 줄이 `VERDICT: PASS|FAIL`) |
| release | `06-release.md` |

## 3. 핵심 제약: "진짜 다른 에이전트"

한 컨텍스트가 여러 사람인 척하는 것을 금지한다. 그래서:

- 모든 산출물은 **해당 에이전트가 직접 파일로 쓴다.** 메인 세션은 내용을 쓰지 않고 전달만 한다.
- Claude Code 서브에이전트는 다른 서브에이전트를 부를 수 없다. 그래서 리더는
  **배분안을 돌려주고**, 메인 세션(비서실)이 그 배분대로 팀원을 각각 띄운다.
  배분의 결정권은 리더에게 있고, 메인은 실행만 한다.

## 4. 한 팀이 일하는 방식 (team-run)

```
CEO 지시 ─▶ [리더: 계획]  ──ASSIGN 목록──▶ 비서실
                                            │ 병렬 실행
                              ┌─────────────┴─────────────┐
                         [팀원 A]                     [팀원 B]
                     <팀>/<A>.md 작성             <팀>/<B>.md 작성
                              └─────────────┬─────────────┘
            [리더: 검토] ◀──────────────────┘
               ├─ REWORK <팀원>: 피드백  → 해당 팀원 1회 재작업 → 다시 검토
               └─ DONE → NN-<팀>.md 작성 (다음 팀의 입력)
```

재작업은 팀원당 1회까지. 무한 루프를 막는다.
리더의 배분안은 `_plan.md`로 남긴다 — 검토 때의 리더는 새로 띄운 에이전트라 이 파일 없이는 자기 계획을 모른다.
팀을 다시 돌리면 이전 산출물과 팀원 폴더를 `.r<N>`으로 옮긴다. 이전 회차가 이번 회차의 입력에 섞이지 않게 하기 위해서다.

## 5. 회사 전체 흐름 (company)

1. 작업 공간 `output/<slug>/` 생성, CEO 지시를 `brief.md`에 기록
2. 리서치~QA 5개 팀을 순서대로 team-run. 각 팀은 앞 팀들의 `NN-*.md`를 읽는다
3. 팀이 끝날 때마다 CEO에게 리더의 3줄 보고 전달
4. `05-qa.md` 마지막 줄이 `VERDICT: FAIL`이면 dev·QA 산출물을 `.r1`로 옮기고 dev 재가동 → QA 재검증.
   `05-qa.r1.md`의 존재가 곧 "재작업 1회 사용" 기록이라 중간에 끊겨도 상한이 유지된다
5. 끝나면 CEO 최종 보고 + `/agent-company:release` 안내.
   배포 준비를 자동으로 잇지 않는 이유: 공개 플러그인이라 누가 어떤 계정으로 쓸지 모르고,
   배포준비팀은 `app/` 설정을 바꾸므로 사용자가 QA 결과를 보고 시작 시점을 정해야 한다

## 6. 파일 계약

```
output/<slug>/
  brief.md                 CEO 지시
  01-research/<에이전트>.md  팀원 작업물 (팀 내부)
  01-research.md           리더 최종 산출물 (다음 팀 입력)
  ...
  app/                     dev 팀 코드
```

## 7. 의도적으로 뺀 것

- 상태 파일·재개 스크립트: 산출물 파일이 곧 진행 상태다. `NN-<팀>.md`가 있으면 그 팀은 끝난 것.
  같은 지시를 다시 실행하면 `brief.md`가 같은 작업 공간을 찾아 이어 간다.
- 팀 간 위원회·에스컬레이션: CEO가 단계 보고를 보고 직접 개입한다.
